A module is a group of implementation units that jointly provide a responsibility through a defined interface. A configured file boundary identifies a declared group; a directory identifies a location. Neither alone proves that the group controls one coherent responsibility. An ownership candidate must identify actual implementations, their consumers and the distinct rules or resources involved, and explain what remains uncertain.

## Completion criteria

1. An initial LaunchPoint scan follows its internal alias imports, separates external packages from missing internal edges, and does not rank the copied SDK as application cleanup work.
2. Production dependency findings disclose their source and role; tests and grouping artifacts cannot masquerade as confirmed production file cycles.
3. The default report presents a bounded, useful set of module subjects with exact evidence and recovery, while preserving the complete underlying findings for programs and further inspection.
4. Unknown responsibility or intended direction remains explicit. A module-overload candidate must have evidence beyond line count or a single function's complexity.
5. First-use behavior and actual-diff behavior share consistent providers, with source/configuration omissions and changes properly represented.
6. The implementation and real-repository checks pass; useful findings, false alarms, remaining limits and model-audit results are reported honestly. No claim of universal architectural judgment or proven agent superiority is required or justified by this work alone.
