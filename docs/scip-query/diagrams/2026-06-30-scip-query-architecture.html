scip-query Architecture

This diagram explains scip-query as a code-intelligence tool: a program that turns real project files into a queryable body of compiler, source, semantic, and git evidence, then runs focused analyses over that evidence.

Runtime shell

The command-line layer resolves project config, opens the active SQLite index, registers commands, and renders text or JSON.

Indexing pipeline

Reindexing detects language projects, runs SCIP indexers, merges their output, converts it to SQLite, and publishes fresh artifacts.

Evidence model

The central read model combines SQLite rows with source facts, AST facts, semantic provider facts, caches, and git/config policy.

Query families

Navigation, graph, cleanup, impact, frontend, quality, health, and diff-gate commands are different views over the same evidence.

What The Main Concepts Mean

Architecture

The architecture is the arrangement of this program's parts by which project files become reliable answers. In this repo, the important parts are the runtime shell, indexing pipeline, evidence store, read model, and query families.

SCIP

SCIP is a compiler-produced code-index format: a structured record of documents, symbols, definitions, and occurrences that lets tools identify code by compiler-resolved identity instead of by text search alone.

Index

An index is the stored representation of code facts created so later commands can search and analyze the project quickly without re-reading every file from scratch.

Read Model

A read model is an object shaped for answering questions rather than storing raw facts. ProjectIndex is the main read model here: it presents definitions, caller maps, callee maps, source references, and file dependencies to query code.

Evidence Graph

The evidence graph is the connected body of facts the queries use: SCIP rows, source facts, AST facts, semantic TypeScript facts, git/config policy, and cached relationships. Its essential role is to explain why a command's answer is justified.

Health Score

The health score is a summarized quality signal built from multiple query families. It is not a separate database; it is an aggregate report over dead code, isolation, duplication, wrappers, drift, complexity, frontend pressure, suppressions, and git evidence.

How To Read It

  • Indexing path: real project files enter src/reindex/index.ts; language indexers produce SCIP output; scip-query converts and publishes a fresh SQLite database.
  • Command path: a user command enters runtime descriptors; execution wrappers open the active ScipDatabase; query functions run over the shared evidence; renderers return text or JSON.
  • Optimization boundary: performance work mostly belongs in reindexing, database access, evidence caches, semantic providers, and query algorithms. The runtime descriptor layer should usually stay thin.
  • Health boundary: health and diff-gate are consumers of the evidence system. They should improve when low-quality evidence or analyzer noise improves, but they should not become the only place where correctness is enforced.
